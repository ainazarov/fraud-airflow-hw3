# HW3 — переобучение модели в Airflow

Kafka → скоринг → Kafka → PostgreSQL. Результат содержит `score`, `fraud_flag` и `model_version`. Airflow и сервисы скоринга запускаются в одной сети Docker Compose. Обучение и инференс выполняются на CPU.

## Запуск

Нужны Docker, Docker Compose v2 и Bash/WSL.

```bash
git clone https://github.com/ainazarov/fraud-airflow-hw3.git
cd fraud-airflow-hw3
docker compose up --build -d --wait --wait-timeout 300
```

- [Airflow](http://localhost:8080) — логин `admin`, пароль `admin`.
- [Модели](http://localhost:8081/models/) и [HTML-отчёт DQ](http://localhost:8081/dq_reports/latest.html).

Адреса открываются на компьютере с Docker. Порты и параметры задаются в `.env.example`; для изменения скопируйте его в `.env`.

По умолчанию создаются 4 500 синтетических размеченных строк за три месяца и исходная модель. Для обучения на `train.csv` из HW1 перед первым запуском в новом томе задайте в `.env`:

```dotenv
DATA_DIR=/absolute/path/to/dataset
TRAINING_CSV=/data/train.csv
```

CSV должен содержать `target`. Существующая витрина при повторном запуске не заменяется.

## DAG и обучение

| DAG | Расписание | Действие |
|---|---|---|
| `advance_month` | Каждые 10 минут | Выбирает существующие строки, переносит `transaction_time` в следующий месяц, добавляет 3 000 строк и удаляет историю старше 36 месяцев |
| `retrain_model` | Каждые 5 минут | Готовит выборку, обучает, сравнивает модели и публикует принятую версию |
| `data_quality` | Каждые 5 минут | Проверяет данные и сохраняет HTML-отчёт |

У всех DAG `catchup=False`. Функции задач находятся в `pipeline/` и имеют docstring с описанием входов, выходов и повторного выполнения. В `dags/` собираются графы задач.

Цепочка переобучения: `prepare_window → train_candidate → evaluate_candidate → publish_candidate`.

Окно фиксировано: **три последовательных месяца**, первые два — train, последний — test. При сдвиге добавляется новый месяц и исключается старейший. Повтор задачи использует сохранённый снимок данных; указатель месяца меняется только после успешного сохранения и публикации модели. Повтор поставки с тем же `run_id` не добавляет месяц дважды. Следующая поставка ждёт принятия модели для последнего месяца витрины.

Модель — Random Forest. Собственный препроцессинг в `pipeline/features.py`: логарифмы суммы и населения, циклические признаки часа и дня недели, расстояние до продавца и one-hot-кодирование категорий. Преобразователи обучаются только на train и используются также при скоринге; `target`, имена и адреса в признаки не входят.

Модели сохраняются в `/opt/project/storage/models/`, общем для Airflow и скорера. После публикации атомарно обновляется `current.json`. Скорер загружает новую модель при обработке следующей транзакции **без перезапуска контейнера** и записывает её версию в результат.

## Проверка качества модели

Кандидат и действующая модель оцениваются **на одинаковых строках последнего месяца** по Average Precision (`average_precision_score`) и ROC-AUC. Публикация разрешена, только если обе метрики конечны и не хуже действующей модели; равенство допускается с погрешностью `1e-12`.

При ухудшении любой метрики кандидат не публикуется, активная версия и указатель месяца сохраняются. Первая модель публикуется после проверки данных и метрик, поскольку предыдущей версии ещё нет. Решения и метрики доступны в [reports/decisions/](http://localhost:8081/reports/decisions/).

## Data Quality

Отдельный DAG проверяет последние три месяца витрины:

- Наличие обязательных столбцов и отсутствие пропусков.
- Непустые уникальные ID транзакций.
- Корректные даты и три последовательных месяца без пропусков.
- Не менее 50 строк и оба класса в каждом месяце; `target` только 0 или 1.
- Конечная сумма в диапазоне `[0, 10 000 000]`.
- Конечные широты в `[-90, 90]` и долготы в `[-180, 180]`.
- Целое население в `[0, 100 000 000]` и непустые категории.
- Все даты train строго раньше дат test.

Задачи: `check_dataset → enforce_quality`. HTML и JSON записываются в `/opt/project/storage/dq_reports/`, рядом с `models/`, до завершения проверки. При нарушении правил DAG завершается ошибкой, отчёт остаётся доступен.

## Проверка работы

В Airflow запустите **Trigger DAG** для `advance_month`, дождитесь завершения, затем запустите `retrain_model`. В Graph видна цепочка задач. После принятия модели в `models/` появляется новый файл, а [current.json](http://localhost:8081/models/current.json) содержит её версию. Для отчёта запустите `data_quality`.

Полная автоматическая проверка на стандартных синтетических данных:

```bash
bash scripts/demo.sh
```

Скрипт поднимает сервисы, выполняет тесты и три DAG, отправляет транзакции в Kafka и проверяет новую `model_version` в PostgreSQL и отсутствие рестарта скорера. Результаты сохраняются в `reports/`.

Посмотреть последние скоры:

```bash
docker compose exec postgres psql -U airflow -d airflow -c \
  'SELECT transaction_id, score, fraud_flag, model_version FROM scores ORDER BY sequence DESC LIMIT 20;'
```

Успешный DAG может завершиться без публикации, если новый месяц ещё не поступил или кандидат оказался хуже. На реальном CSV сначала обрабатываются существующие месяцы по порядку; поставка новых месяцев ждёт завершения этой истории.

[Результаты проверки](reports/RESULTS.md): 99 тестов, смена версии без рестарта и отклонение худшего кандидата на данных HW1.
