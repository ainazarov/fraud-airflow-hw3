## Границы проверки и воспроизведение

Реальный CSV проверялся сценарием
[`scripts/real_data_check.py`](../scripts/real_data_check.py) через те же функции
`prepare_window → train_candidate → evaluate_candidate → publish_candidate`,
которые использует DAG. Этот прогон выполнялся в изолированном хранилище и
**не являлся запуском DAG через Airflow scheduler**. Он подтверждает импорт,
временное разбиение, DQ и фактический отказ в публикации худшего кандидата.

Команда повторения с каталогом исходного CSV на Docker-хосте:

```bash
docker compose --profile tools run --rm --no-deps \
  -v /home/user/datasets/fraud:/data:ro \
  tools python scripts/real_data_check.py \
  --csv /data/train.csv \
  --storage-dir /opt/project/storage/real-data-check
```

Результат сохраняется в
`storage/real-data-check/evidence/real-data-check.json`. Путь внутри JSON описывает
контейнер проверки; исходные значения транзакций в отчёт не записываются.

Проверка фактических DAG, Kafka, PostgreSQL и горячей замены выполняется отдельно
на воспроизводимых синтетических данных:

```bash
bash scripts/demo.sh
```

Она создаёт `reports/e2e.json`, HTML-отчёт DQ и снимки контейнера скорера до/после.
Метрики синтетического примера предназначены для воспроизводимости процесса и
не показывают качество обнаружения фрода на настоящих операциях. Проверочный
месяц обоих режимов участвует в выборе модели, поэтому не является независимой
финальной оценкой после выбора.
